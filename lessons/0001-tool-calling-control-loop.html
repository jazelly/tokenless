Lesson 0001 · Tool-Driven Agent Runtime

Who actually calls the tool?

到底是谁调用工具？把“模型选择”和“系统执行”拆开，你就能判断 Tokenless 应该做 adapter 还是完整 runtime。

Verdict / 结论： Yes—the abstract pattern is “show the model an available capability contract, then let it propose a call.” But the model only proposes. The Harness chooses what to expose, validates and authorizes the proposal, executes code, returns results, and decides whether another model turn is needed.

对，抽象模式就是“把可用能力契约展示给模型，让模型提出调用”。但模型只负责提议；Harness 负责暴露范围、校验、授权、执行、回传结果和续轮。

1. Registry is not the menu / Registry 不等于菜单

A registry contains executable code and private runtime behavior. The model receives only a projection: name, description, and argument schema.

Registry 包含执行函数、权限、超时、取消和 UI。模型只收到它的投影：名称、描述与参数 schema。

ToolDefinition (private)
  ├── name ───────────────┐
  ├── description ────────┼──▶ ToolSchema (model-visible)
  ├── parameters ─────────┘
  ├── execute()
  ├── authorization / timeout / cancellation
  └── presentation

2. The model requests; it does not execute / 模型请求，不执行

Harness menu → model proposal → Harness gate → real execution → result → model

The phrase “the model called a tool” is shorthand. For a client-side function tool, the model emitted structured intent such as {name, arguments, call_id}. Nothing has touched the filesystem yet.

“模型调用了工具”只是简称。对 client-side function tool 而言，模型只输出了结构化意图；这时文件系统还没有发生任何变化。

3. Native channel and text envelope / 原生通道与文本信封

Native structured callText envelope
Capability advertisementProvider tools fieldSystem prompt catalog
Model outputTyped tool_call event/blockMarked JSON text
ParserProvider adapterTokenless
Abstract semanticsModel proposes a callModel proposes a call
Main differenceProvider supplies framingTokenless must enforce framing

So a text protocol is not fake merely because it is text. It can faithfully emulate the client-visible contract. It is weaker operationally because malformed prose, duplicate envelopes, truncation, or prompt injection must be handled by Tokenless rather than by a provider-native response channel.

所以文本协议并非天然“假 tool call”。它可以忠实模拟外部契约；只是 framing、解析与抗干扰责任落到了 Tokenless。

4. The decisive architecture question / 真正决定架构的问题

If DeepSeek Harness is the caller: it already owns ToolDefinition, execution, tool results, and the agent loop. Tokenless only needs to translate one model turn: OpenAI-style schemas in, web prompt out, parsed OpenAI-style tool calls back. The caller sends the next request after execution.

如果调用者是 DeepSeek Harness：它已经拥有工具定义、执行、结果和循环。Tokenless 只需翻译一次模型 turn；执行完之后的下一轮由外层 Harness 发起。
If Tokenless promises a completed autonomous task: Tokenless must own the registry, executors, results, and continuation loop because no outer runtime will do it.

如果 Tokenless 自己承诺完成 autonomous task：它才需要完整拥有 registry、执行器、结果与续轮循环。

5. Apply it to this repository / 套回当前仓库

packages/harness/src/internal/system-prompt.ts already serializes a tool catalog into the prompt and asks the web model for an action_batch envelope. That is the text-envelope version of the same abstract control loop.

Meanwhile, the OpenAI-compatible API proxy currently rejects tools. Bridging those two boundaries does not automatically require copying DeepSeek Harness's execution runtime into Tokenless.

Retrieval check / 回忆检验

At the instant a model emits a tool call, what has definitely happened?

Only a call proposal has been produced. The Harness still has to parse, validate, authorize, execute, and correlate a result.

When does Tokenless need its own full Agent Loop?

When Tokenless, rather than an outer Harness, owns the promise to execute calls repeatedly until a final answer is produced.
